# X stock cashtag rankings

How often US-listed **stock and ETF** cashtags (e.g. `$NVDA`) were mentioned on [X](https://x.com) in a trailing **5-hour** window, plus which ones are **rising**. Everything comes straight from X: official recent post counts and a few post samples. No third-party "trending" lists are used.

**Stocks/ETFs only** (no crypto coins). Updated **every 5 hours** on `main`, with runs at 01:14, 06:14, 11:14, 16:14 and 21:14 Europe/Berlin time. All timestamps in the data are UTC.

**Latest:** [`data/latest.json`](data/latest.json) · **Today (every ticker seen this UTC day):** [`data/today.json`](data/today.json) · **Past days:** [`data/daily/`](data/daily/) · **History:** [`data/history/`](data/history/)

Built by [Adanos Sentiment](https://adanos.org) (`@adanos_api`).

> **Method change on 2026-10-17 (method v4, `query_mode: bare`): counts are no longer `$TICKER` cashtag counts.**
> Since about 04:23 UTC on 2026-10-17 the free X tools strip the `$` from every query
> (`$ was removed from query, because X's search API does not accept that character`). From that day the rankings count the
> **bare ticker** (`NVDA -is:retweet <spam filter>`), which also matches plain-text and company-name mentions. Bare counts are
> therefore **not directly comparable** with the cashtag counts before 2026-10-17 (test 2026-10-17 00–05 UTC: bare NVDA 617 posts
> with the spam filter, vs 412 for `$NVDA` in the same hours one day earlier). `latest.json` and `today.json` carry a `method_note` and `query_mode`.
> - **Ambiguous tickers are not measurable** in bare mode: 1–2 letter tickers and tickers that are common words
>   (English word frequency zipf ≥ 3.0, or ≥ 4.0 in de/fr/es/it/pt/nl, plus curated slang/acronyms), e.g.
>   A, ALL, NOW, ON, IT, ARE, CAN, FUN, GO, CAR, SO, OPEN, AI, NET, APP, DIA, BE, BA, plus names that collided in the first bare
>   runs (SOFI, SHOP, BABA, MARA, NIO, PDD, CRM, HAIN, HAO, HAVA): **1,377 tickers**, listed in
>   [`config/ambiguous_tickers.txt`](config/ambiguous_tickers.txt) (generated by `scripts/gen_ambiguous.py`). They are left out
>   of the sweep and the ranking (`latest.json` → `not_measurable`). A not-measurable ticker is never counted individually
>   (not as a core daily count, not as a hot re-read of an earlier count), never stored in `hourly.json`, and never listed in
>   `latest.json`, `today.json` or the daily files (`check` enforces it; `purge-not-measurable` cleans up after the list grows).
> - **Context tickers:** ten big ambiguous core names ([`config/context_tickers.txt`](config/context_tickers.txt): META SPY MU HOOD
>   COIN ARM AMC UBER SNOW RIOT) are counted every run, but only with a finance-context word:
>   `META (stock OR stocks OR shares OR earnings OR calls OR puts OR ... ) <spam filter>`, label `context-required`.
>   Test 2026-10-17: a bare `META` sample had 3/25 posts about the company/stock (the rest: "meta" in games, Spanish/Portuguese
>   "meta"); with the context clause 15/25.
> - **Scaling:** the ranking uses `rank_score` = count × `clean_share_est`, where the share now means "sampled posts matched by
>   the bare query that are real stock mentions": the post contains the `$TICKER` cashtag, or the ticker plus stock context
>   (a finance word from [`config/context_terms.txt`](config/context_terms.txt) or another `$cashtag`; context tickers must be
>   upper case). 6 own recency samples per run; prior 0.5 until evidence accumulates (cashtag-era shares were reset).
> - Split tree, hourly series and own-sample evidence of the cashtag era are not mixed with bare counts (reset on the mode change).
> - **Word-collision guard:** a ticker whose bare 5h count is more than **8×** the median of its `$cashtag` 5h counts before
>   2026-10-17 (bare count ≥ 50), or that has no `$cashtag` history and a bare count above **300**, is held back
>   (`held_back`, label `suspected-word-collision`) and queued (`collision_queue`) for an own recency sample in the next run. Once
>   ≥ 10 own sampled posts (72 h) show **≥ 30 %** real mentions it is ranked with the cleaned estimate (label
>   `collision-check-passed`). Tuned on the 11:17 Berlin run of 2026-10-17: SHOP 10,901 bare vs median 21 `$SHOP`, BABA 6,669 vs 34,
>   MARA 1,783 vs 27, NIO 353 vs 35, CRM 296 vs 20.5, PDD 140 vs 6.5 (10–520×) were caught; TSLA, AMD, NVDA, QQQ, CRWV were
>   1.2–4.7×.
> - **Automatic switch back:** every bare run starts with one probe read `$NVDA -is:retweet`. If the tool no longer reports that the
>   `$` was removed, the run switches `data/query_mode.json` back to `cashtag` and re-plans with `$TICKER` queries.

## Method (since 2026-10-12, method v3: `group-sweep+adaptive-splits+sampling+daily-counts`)

The question is *which tickers X users are talking about today*, so breadth comes first. X has no "top cashtags" API, and each X read gives one count or one small sample of posts. A run spends about **90 reads** (+ ≤ 10 retries; numbers below are the cashtag-era v3 layout, the current bare-mode plan is under *Read budget*):

| Step | Reads per run | What it does | Exact or sampled |
|---|---|---|---|
| 1. Group sweep (stocks) | 13 | **Every US stock except the 10 megacaps (~5,410 tickers, the rest of the core included)** is packed into OR-groups: `($A OR $B OR ...) -is:retweet <spam filter>`, ≤ 4096 characters (~360–430 tickers per group), each counted with 29 hourly buckets. | Exact group counts |
| 1b. Group sweep (ETFs) | 3 | The ~5,470 ETFs (minus SPY/QQQ) in 14 groups; **3 rotate per run**, so every ETF group is screened about once a day. | Exact group counts |
| 2. Megacaps | 10 | [`config/megacaps.txt`](config/megacaps.txt) (SPY, QQQ, NVDA, TSLA, AAPL, MSFT, AMZN, META, GOOGL, PLTR) are counted individually every run. | Exact individual counts |
| 3. Adaptive splits | up to 24 | Hot groups are cut into 4 parts, recursively ("drill chains", below). The split tree is kept across runs in [`data/splits.json`](data/splits.json). | Exact group counts (one part per split by subtraction) |
| 4. Sampling | 10 | 6 relevancy-sorted samples (25 posts) of the hottest groups/split parts (per ticker), then 4 co-mention samples on new tickers, unverified split leaves or the last risers. | **Sampled** |
| 5. Daily exact counts | ~31 | One 29h count per ticker **per UTC day**: split leaves, sample discoveries that pass the clean check, the core not yet counted today (≥ 10 per run, so all 50 get one a day), and re-reads of tickers that are still hot (5h count ≥ 60, ≤ 8 per run). | Exact individual counts |
| Spare | 4 | Retries and invalid requests. | |

**Adaptive splits (heavy-hitter search):** a split cuts a node (a group or part) into 4 contiguous parts. If the node was counted in this run, 3 parts are counted and the 4th is *node − 3 parts* per hour (≥ 0; posts that mention tickers of two parts make it an under-estimate, and the run reports any `overlap_warning`); a node counted in an earlier run needs all 4 parts. The script splits in this order: (1) continue into a part created in this run that holds ≥ 1.6× its fair share of the parent's posts, (2) resume such a part from an earlier run, (3) start on a root group not split yet, (4) re-split a root whose old parts are stale; within a class the node with the most posts in the last 24h goes first. Counts of tickers already measured individually in the last 30h are subtracted before choosing ("explained away"), so core names inside a group don't attract every drill. Nodes with ≤ 3 tickers are leaves: their members get exact daily counts. A drill to one busy ticker costs ~12 reads (400 → 100 → 25 → 7 → 2). The tree is validated on every plan and build and the script **fails closed** if it is inconsistent; parts not re-measured for 30h are pruned and cold splits collapse.

**What is exact:** every ranked number is an exact X count, `GET /2/tweets/counts/recent` over the identical 5-hour window. A group or part count is the exact number of posts mentioning *any* of its tickers (a post with several counts once), so it is an upper bound for every member, and a quiet group proves all its tickers are quiet.

**What is sampled / searched:** *which* non-megacap tickers get an exact count. Splits find tickers that dominate a group's volume; samples find tickers that are co-mentioned; a ticker that is moderately busy inside a busy group and rarely sampled can still be missed. `latest.json` ranks **the tickers counted individually in that run** (megacaps + that run's daily counts); [`data/today.json`](data/today.json) lists everything seen during the UTC day.

**`data/today.json` (daily aggregate):** the **current UTC calendar day** (00:00 UTC up to the latest run's `window_end`; not a rolling 24h). Every ticker with an exact count today or with clean sample posts today, with
- `status`: `exact` (every hour of the day so far counted individually; `count` is exact), `partial` (some hours exact: `exact_part`; the rest only bounded), `bounded` (only an upper bound), `seen` (sampled, no count),
- `upper_bound`: exact hours + for every other hour the smallest measured group/part containing the ticker (subtracted parts are not used as bounds),
- `first_seen`, `last_measured`, `sources` (`megacap`, `core-daily`, `split-leaf`, `sample`, `hot-reread`), `sample_clean_share`, `held_back` (+ reason),
- `windows_5h`: exact 5h window counts **back-filled from hourly buckets** (one 29h read covers every earlier window of the day).

The previous day is finalised in `data/daily/<YYYY-MM-DD>.json` (re-written by the runs of the following day, which back-fill its last hours). The hourly series behind it are in `data/hourly.json` (last ~2 UTC days).

### Counting details

- **Individual query:** `$TICKER -is:retweet <spam filter>` (bare mode since 2026-10-17: `TICKER -is:retweet <spam filter>`, context tickers with the finance clause) for **every** ticker (megacap, daily count): original posts, replies and quotes, reposts excluded, spam terms excluded. No language filter. **Collision tickers** (below) also get per-ticker terms. (Before 2026-10-10 only collision tickers carried the spam filter; that is how `$TM` got to #5 with memecoin spam.)
- **Hourly series:** `granularity=hour`, from `window_end − 29h` to `window_end`. One read gives the 5h window (last 5 buckets), the same 5 hours yesterday (first 5 buckets) and the hourly shape.
- **Window:** the last 5 full UTC hours before the run. For example, a run at 14:14 UTC counts 09:00–14:00 UTC.
- **Ranking:** by `rank_score` = `rank_score_raw` × `clean_share_est`, i.e. the estimated count of real (clean) posts; `mentions_clean_est` = `mentions` × `clean_share_est`. `rank_score_raw` is the exact 5h count with collapsed bursts capped (see below). `mentions` always stays the exact raw count.
- **Momentum:**
  - `momentum_5h_vs_prev_day` = (5h + 1) / (same 5h yesterday + 1)
  - `momentum_last_hour_vs_prev_9h` = (last hour + 1) / (average of the 9 hours before + 1)
  - `mentions_last_hour_prev_day` = the same hour yesterday
  - The +1 keeps tickers with no posts yesterday from producing infinite ratios.
- **Risers:** `rank_score` ≥ 20 and one of the two momentum values ≥ 3. The last-hour ratio only counts if the last hour is also ≥ 2× the same hour yesterday; otherwise every big name became a "riser" at the US open (2026-10-09 14:00 UTC: 38 risers incl. SPY, TSLA, MSFT). They are listed separately in `risers` and get the label `riser`.

### Spam, bots and collisions

Audit 2026-10-10 (Oct 9/10 snapshots, ~13 relevancy samples of 25 posts): large caps are mostly real chatter
(`$PLTR` ~70% clean, `$SPCX` ~75%), but several published entries were not about the stock at all:
`$TM` #5 (Toyota: 0 of 50 sampled posts; a Solana memecoin "TeleMoney" plus WhatsApp/Telegram scam templates),
`$GOLD` (0 of 22 about Barrick: XAUUSD forex signals and a token reply farm), `$MARU`, `$CALI`, `$MATE`, `$CGPT`
(memecoins/tokens), and the small-cap runners `$WFF $YMAT $ZYBT $SAIQ $FRGT` were real movers but ~70% of their
posts were ticker dumps and "DM me" lists.

- **One spam filter, applied everywhere:** [`config/spam_filter.txt`](config/spam_filter.txt) is appended to every X query of a run: group sweeps, every individual count (core, candidate, carryover) and every sample. It targets what the audit found: WhatsApp/Telegram pump groups (`-whatsapp -telegram -tg -"stock analyst" -"hot stocks" -"discussion group" -"investment advisor" -"join for free" -"exclusive group" -"Ms. Victoria" -"follow him" -"dm me" -challenge -signals`), reply-shill campaigns (`-mexc -"my go to"`), vote/listing templates and memecoin calls (`-vote -leaderboard -coinmarketcap -"listing id" -memecoin -solana -mcap -marketcap -mc -ca -"my call" -token -crypto ...`). The suffix is ~450 characters, so a stock group now holds ~330–430 tickers (13 groups instead of 12; the core counted individually shrinks from 50 to 49 to keep ~95 reads).
- **Impact, 2026-10-10 09–14 UTC, published unfiltered → filtered:** NVDA 650→530, TSLA 425→302, AAPL 149→98, PLTR 252→223, GME 180→140, SPY 295→221, ASTS 388→361, IREN 240→182, TM 338→49 (then removed by the collision terms / clean check). The big-cap cut is mostly spam (a sample of removed NVDA posts was 25/25 the "US Stock Market WhatsApp Group" template; posts hit only by the new terms were ~85% spam), but **~15% of what the new terms remove on large caps is legitimate** (e.g. "Token Factory", "bullish signals"). So counts are now systematically 10–35% lower than before 2026-10-10 and not directly comparable.
- **Collisions:** [`config/collisions.txt`](config/collisions.txt) adds per-ticker terms for cashtags shared with coins, tokens or greetings (GM, AI, U, STX, SKY, PUMP, S, W, SI, SM, TM, OGN, QNT, ...); label `collision-filtered`, the entry carries its `query`. Cashtags with no stock chatter at all are excluded ([`config/exclude_tickers.txt`](config/exclude_tickers.txt)): BTC, ETH, SUI, ... and since 2026-10-10 GOLD, CALI, MARU, MATE, CGPT.
- **Ticker dumps and templates (sample level):** X counts can't filter by the number of cashtags, so the samples do it. A sampled post is **not clean** if
  - its author is in [`config/spam_accounts.txt`](config/spam_accounts.txt) (grown from the audit),
  - the same normalized text comes from ≥ 3 authors (template),
  - it is a **ticker dump**: > 8 cashtags, or ≥ 4 cashtags with < 8 real words once cashtags, links, @mentions, #hashtags, numbers and emoji are removed,
  - or it contains a filter term (whole-word match).
  - or it is crypto/memecoin context (local check, no query cost: contract addresses, crypto-flavoured @handles, words like cardano, solana, memecoin, degen, gems, lore, presale, "20x profit"/"185x up from"; not bitcoin/btc or "meme stock"), added 2026-10-11 after `$HODL` (VanEck Bitcoin ETF) was discovered from memecoin posts,
  - or it has fewer than 3 real words ("$hodl gang", "20x on $TM").
- **Clean check for non-core tickers (split leaves included):** a ticker found by splits is counted, but only ranked if samples (this run, today's pooled samples, or a passed check ≤ 24h old) show clean posts; split leaves without such evidence get a co-mention sample when slots allow. A discovered ticker becomes a candidate only with clean posts from ≥ 3 distinct authors and (with ≥ 5 sampled posts) a clean share ≥ 30% (deliberately loose: in the 2026-10-10 04–09 UTC samples `$SPCX`, a real and busy stock, had 38% because its co-mention samples were full of dumps; `$TM` had 1 clean author and fails). A carryover ticker is re-checked when this run's samples mention it, otherwise its last passed check (≤ 24h) is carried (label `clean-check-carried`); without one it is not carried over. A non-core ticker that fails is not ranked; it is listed in `held_back` with its exact count and the reason.
- **Clean share (ranks):** every run takes 4+ **own** recency samples (`smp-o-<T>`, the ticker's own query, newest posts) of the likely top / least-evidenced tickers. `clean_share_est` = (clean + 10 × prior) / (posts + 10) over the ticker's own samples of the last 72h; prior = pooled own-sample share (default 0.8; label `clean-share-prior` when the ticker has no own evidence). Below 30% → `low-clean-share`. `sample_clean_share` comes from co-mentions in other samples (mostly list dumps, e.g. META 9% vs 92% in its own posts, 2026-10-13) and is informational only.
- **Crypto:** a post is crypto if it carries ≥ 2 crypto cashtags (BTC, ETH, XRP, QNT, …), any USDT/USDC, an `X/USDT` pair or words like altcoin/blockchain/on-chain/defi/web3. A non-core ticker whose sampled posts are ≥ 40% crypto (≥ 5 posts) is held back (`crypto-collision`). `$QNT` is excluded.
- **Group activity score (`heat`):** excess over each group's baseline, with the baseline scaled by the median ratio of all groups of the same kind in the run. Before 2026-10-11 it was unscaled, so in quiet-market runs (Saturday vs Friday evening) every group scored 0.0 and sample groups were picked by tie-break.
- **Bursts:** an hour above 6 × max(29h hourly median, 3) that collapses in the next hour (to less than a third) is a bot or pump burst. It is labelled `burst`, listed in `burst_hours`, and that hour is capped at the limit in `rank_score`. A spike in the **last** hour can't be judged yet: it gets the label `spike-last-hour` (only if the last hour is also ≥ 2× the previous 9h average; fixed 2026-10-10, `$TM` had it with 40 vs a 9h average of 81.7) but is not down-weighted, so real breakouts are not penalised.

### Universe

[adanos-software/free-ticker-database](https://github.com/adanos-software/free-ticker-database) `data/core_listings.csv`, filtered as follows:

- `Stock` + `ETF` on NASDAQ, NYSE, NYSE ARCA, BATS or NYSE MKT
- tickers matching `^[A-Z]{1,6}$`
- minus [`config/exclude_tickers.txt`](config/exclude_tickers.txt)

It is stored in [`data/universe.csv`](data/universe.csv) (10,898 symbols on 2026-10-08), with the source commit in [`data/universe_meta.json`](data/universe_meta.json).

### Read budget

- Since 2026-10-17 17:00 Berlin: about **90 planned X reads per run** (bare mode: 1 probe, 14 stock + 3 ETF groups, 18 megacap/context counts, ≤ 18 split parts, 10 samples = 3 group + 1 co-mention + 6 own, ~23 daily counts, 3 spare), plus a reserve of at most 10 retry reads (**≤ 100 per run**). Group queries are packed to **≤ 3,000 characters** (before: ≤ 4,096; the 503s of 2026-10-17 hit ~4,090-char queries), which gives 14 stock and 16 ETF groups. 5 runs a day uses ≤ 500 reads per UTC day, inside a 600-reads-per-day cap shared with other jobs. Unused split/discovery slots are simply not spent.
- Per day: ~80 group reads (every stock group 5×, every ETF group ~1×), 50 megacap reads, ≤ 120 split reads, 50 samples, ~155 exact daily counts (all 50 core + ~100 discoveries/re-reads).
- The script generates every query (groups, split parts, tickers, samples) and prints the single next call; the operator never builds one.
- X calls are made strictly one at a time, with a ~6 s pause after each one (≤10 calls per minute). On a 429: wait 90 s, then 240 s, then give up and pause 300 s before the next call. On a 5xx (e.g. 503): wait 20 s and retry once; a second 5xx skips the call. A run takes about 45–55 minutes.
- A call that fails 3 times (429) is skipped.
- A run stops after 8 5xx errors, after 5 other errors (neither 429 nor 5xx), or when the retry reserve is used up.
- If a run ends early but all stock groups and all 10 megacap counts are done (ETF groups, split parts and samples may be missing: listed in `missing_calls`, with a note in today.json; a missing ETF group is counted first in the next run), it is published with `"partial": true` and a `partial_reason`. Otherwise nothing is published.
- If fewer reads are left, the script shrinks the daily counts first (to 10), then splits (to 9), ETF groups, samples, spare, then the rest; megacaps last.
- A run is skipped if fewer than ~20 reads fit.

### Known risks and limits

- Discovery is searched, not exhaustive: splits find tickers that dominate a group's volume (≥ 1.6× fair share per level), samples find co-mentioned ones (25 posts per read). A moderately busy ticker inside a busy group can be missed. Relevancy order with few results can bunch near the end of the window.
- Subtraction under-estimates the 4th part when posts mention tickers of several parts; it only steers the search and is never published or used as an upper bound.
- The core outside the megacaps is no longer counted every run: `latest.json` has it only in the run that does its daily count (or a hot re-read); `today.json` keeps the rest of the day as `partial` + `upper_bound`.
- `today.json` is exact only for `status: exact`; `partial`/`bounded` entries carry an upper bound from group counts, which can be far above the truth for tickers in busy groups.
- The spam filter, collision terms and spam accounts need maintenance as templates change (new campaigns appear weekly). The filter removes some real posts (~15% of what it cuts on large caps; short generic words like `ca`, `mc`, `tg`, `signals`, `challenge`, `token` have false positives).
- Ticker dumps and templates are only detected in the samples (≤ 6 × 25 posts per run). They decide *which* non-core tickers are ranked, but a core ticker's exact count still includes dumps that use no filter word.
- The clean check is a small-sample judgement: a real mover whose chatter is mostly lists (typical for small-cap runners) can be held back, and a well-disguised campaign can pass.
- Coordinated but "real" chatter (pump groups, screener bots, signal channels) is hard to tell apart from organic interest, especially on small caps.
- Group queries are up to 3000-character strings that the operator passes to X verbatim. A copy error silently drops tickers from that group's screen.
- ETFs are only screened about once a day (3 of 14 groups per run).
- Comparability:
  - Snapshots before 2026-10-08 counted `$TICKER` including reposts over a different watchlist.
  - Method v1 runs (2026-10-08 morning) ranked core + hot + rotation tickers with unfiltered counts.
  - Collision tickers such as `$AI` and `$OPEN` are filtered from method v2 on.
  - Method v3 (2026-10-12) ranks megacaps + the run's daily counts instead of a fixed core of ~50 every run, so `ranked_count` and the set of names per snapshot change.

These fields have the same meaning as before:

- `watchlist_size`: the size of the universe.
- `scan_count`, `tickers_measured`: tickers counted individually this run.
- `ranked_count`: entries in `rankings`.

Added fields:

- **Run-level:**
  - `screened_count`: tickers covered by the group sweep this run.
  - `sources`, `x_reads_breakdown`, `ranking_rule`, `risers_rule`, `group_sweep`, `sampling` and `risers`.
  - `adaptive_splits`: the split rule, reads, prune notes, and every split of the run (node, parts with size/range/mentions, `subtracted`, `overlap_warning`); `state` says whether the tree was saved.
  - `freshness`: every ranked ticker was counted in this run; per entry `last_measured` is the time of its count.
  - `x_reads_breakdown` adds `split_counts`, `megacap_counts`, `daily_counts`.
  - `partial` / `partial_reason`: `true` when a run ended early but published, because all stock groups and all megacap counts were done (`missing_calls` lists what is missing). The missing tickers are in `planned_not_measured`, and the `note` starts with `PARTIAL RUN`.
- **Per entry:**
  - `tier`: `core` (megacaps and core) or `discovered`.
  - `source` (v3): `megacap`, `core-daily`, `split-leaf`, `sample`, `hot-reread` (v2 snapshots: `core`, `core-returned`, `carryover`, `discovered`).
  - `last_measured`: when this entry was counted (always in this run).
  - `labels`: `riser`, `burst`, `spike-last-hour`, `collision-filtered`, `low-clean-share`, `clean-check-carried` or `clean-check-pooled-today`.
  - `sample_posts`, `sample_authors` (distinct authors of clean posts), `sample_clean_share` (with ≥ 5 sampled posts).
- `held_back`: non-core tickers that were counted but failed the clean check (`ticker`, `mentions`, `reason`).
- `spam_handling`: the filter, post rules and clean-gate parameters of the run.
  - the momentum and burst fields and `rank_score`.
  - `hourly`: the 5 window buckets.
  - `discovered_via` and `sample_authors` for discovered tickers.
  - `query` for collision tickers.

[`data/next_tickers.json`](data/next_tickers.json) lists the megacaps (the only fixed individual counts of the next run) and the core inside the sweep. Older snapshots in `data/history/` keep their original shape.

## Refreshing (maintainers)

`scripts/build_rankings.py` (Python 3, stdlib only) does all selection logic. The operator makes **one X call at a time**, exactly as printed, and records each result (full procedure: [`docs/RUNBOOK.md`](docs/RUNBOOK.md)):

```bash
python3 scripts/build_rankings.py plan            # window, budget, groups, split tree -> work/run.json
python3 scripts/build_rankings.py next-call       # the ONE next X call (or the next script step: pick-samples,
                                                  # pick-candidates, build)
python3 scripts/build_rankings.py record S01=1471:364,344,...   # KEY=TOTAL:29 hourly buckets (oldest first); pauses 4 s
python3 scripts/build_rankings.py record-sample smp-S07 --lines work/samples/smp-S07.txt
python3 scripts/build_rankings.py record-error S05 --kind 429   # prints WAIT 90s / WAIT 240s / RETRY / GIVE UP / STOP
python3 scripts/build_rankings.py record S07.2=1210:40,38,...   # a split part (the script prints the key and query)
python3 scripts/build_rankings.py build           # complete, or partial if group sweep + megacaps are done
python3 scripts/build_rankings.py abandon --reason "..."   # archive an unpublishable run (nothing published)
python3 scripts/build_rankings.py next            # status: next step, budget, retries, skipped calls
python3 scripts/build_rankings.py check           # offline self-checks (incl. split state); tests: python3 -m unittest discover tests
python3 scripts/build_rankings.py splits-reset    # only after a fail-closed split-state error (no X reads)
```

`TOTAL` is `meta.total_tweet_count`. The script checks that the buckets add up to it, which catches transcription errors. Tunables are the constants at the top of the script; spam, collision and account lists are in `config/`.
